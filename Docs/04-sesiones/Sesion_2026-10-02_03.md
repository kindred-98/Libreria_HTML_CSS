## 1. El síntoma

Al abrir la web en local, la consola del navegador se llenaba de este mensaje
repetido cientos de veces:

```
WebSocket connection to 'ws://127.0.0.1:3001/8f2a4d50f0fd502b11e32944f748bb5ab806f9c0'
failed: Error during WebSocket handshake: Unexpected response code: 400
```

Medio minuto de consola y el desarrollador seguía sin poder ver por qué. La
pregunta era si era un fallo de seguridad, si había que arreglarlo, y si afectaba
a la web.

## 2. De dónde sale el script (no es Live Preview)

El nombre del script inyectado, `/___vscode_livepreview_injected_script`, hace
pensar en la extensión *Live Preview*. No lo es: **Live Preview no está
instalada**. El script lo genera **Live Server**, y el nombre del endpoint es
histórico:

```js
// out/extension.js de ms-vscode.live-server-0.4.20
t.EXTENSION_ID = "ms-vscode.live-server";
t.INJECTED_ENDPOINT_NAME = "/___vscode_livepreview_injected_script";
```

En el repositorio solo hay una extensión de previsualización instalada,
`ms-vscode.live-server@0.4.20`. Y el token que aparece en la URL del error
(`8f2a4d5…`) sí coincide con el que genera ese servidor:

```js
const connection = new WebSocket('ws://127.0.0.1:3001/8f2a4d50f0fd502b11e32944f748bb5ab806f9c0');
```

## 3. La causa: la cabecera `Origin`

Live Server valida `Host` + `Origin` en los dos canales para impedir
DNS-rebinding y Toma de control de WebSocket desde otra página (`CSWSH`). El del
WebSocket aborta el handshake:

```js
class WSServerWithOriginCheck extends WebSocketServer {
  shouldHandle(req) {
    const origin = req.headers.origin;
    return super.shouldHandle(req) && origin && (
      origin.startsWith("vscode-webview://") ||                    // preview embebido
      (this.externalHostName && origin === this.externalHostName)   // http://127.0.0.1:3000
    );
  }
}
// if (!this.shouldHandle(req)) return abortHandshake(400)
```

La comparación es una **igualdad exacta de cadena**. El servidor sirve en
`http://127.0.0.1:3000`, así que `externalHostName` es
`http://127.0.0.1:3000`. Si la página se abre como `http://localhost:3000`, el
navegador manda `Origin: http://localhost:3000`, que no es la misma cadena, y el
handshake se corta con `400`. El script inyectado reintenta en bucle: de ahí la
lluvia de mensajes idénticos.

### 3.1 La incoherencia que lo dispara

El canal **HTTP** sí tiene una excepción para `localhost`, el WebSocket no:

```js
// Canal HTTP → 401 si algo no cuadra
if (req.headers.host !== `localhost:${this._connection.httpPort}` &&
    req.headers.host !== this._connection.host &&
    req.headers.host !== authority
    || req.headers.origin && req.headers.origin !== `${scheme}://${authority}`) {
  return respond(401);
}
```

Es decir: `http://localhost:3000` **carga la página sin problema** y a la vez
**no puede conectar el WebSocket**. De ahí que el error appearanceciera sin
ningún otro síntoma visible. Es un bug de usabilidad de la extensión, no un
agujero.

## 4. Verificado a mano contra el servidor real

Con el servidor en marcha se mandó un handshake crudo a `127.0.0.1:3001` con
distintas cabeceras `Origin` y se leyó la línea de estado:

| `Origin` enviado | Respuesta |
|---|---|
| `vscode-webview://0abc1234.vscode-cdn.net` (embebido) | **101 Switching Protocols** |
| `http://127.0.0.1:3000` | **101 Switching Protocols** |
| `http://localhost:3000` | **400 Bad Request** ← el caso del usuario |
| `https://evil.example.com` (intento de ataque) | **400 Bad Request** |
| *(ninguna: `curl`, `node`)* | **400 Bad Request** |
| `http://127.0.0.1:3000` con una ruta inventada | **101 Switching Protocols** |

Los puertos también se comprobaron: `Get-NetTCPConnection` muestra `3000` y
`3001` escuchando **solo en `127.0.0.1`**, y los dos con el mismo `OwningProcess`
(`code.exe`). No hay ningún proceso ajeno ocupando el `3001`.

### 4.1 Un detalle que sale de la prueba

La última fila no estaba en la lista de hipótesis y conviene escribirlo: con un
`Origin` válido, **cualquier ruta** del WebSocket devuelve `101`. El token de 40
hexadecimales de la URL no se está comprobando. En el código se ve por qué: el
servidor arranca sin fijar `options.path`.

```js
this._connection.wsPath = `/${randomBytes(20).toString("hex")}`;
this._startWSServer(null, /* options.path = null */);
```

Y el chequeo de ruta solo actúa si `options.path` está definido:

```js
shouldHandle(req) {
  if (this.options.path) { /* compara req.url con options.path */ }
  return true;
}
```

Conclusión: el token de la URL es decorativo y **no aporta nada de
seguridad**. La única puerta real es `Origin`, y sin `Origin` no se cuela
nadie. Eso no abre ningún riesgo aquí, pero explica por qué la hipótesis
"token caducado" queda descartada: no hay token que validar.

## 5. Por qué no es una vulnerabilidad

| Comprobación | Estado |
|---|---|
| Escucha en la red local | **No**: `127.0.0.1` en `3000` y `3001` |
| `Origin` de otra web (ataque `CSWSH`) | **Rechazado**, `400` |
| Peticiones sin `Origin` (`curl`, `node`) | **Rechazadas**, `400` |
| Peticiones con `Host` falsificado (DNS-rebinding) | **Rechazadas**, `401` |
| El token de la URL protege algo | **No**, ver `## 4.1` |

El `400` es el control haciendo su trabajo. Un `200` ahí habría sido el fallo.

Lo que sí sería un riesgo real, y que conviene dejar anotado: poner
`livePreview.hostIP` en `"0.0.0.0"`. Entonces el servidor de previsualización
escucharía en **toda la red** con los permisos de este usuario, y cualquier
máquina de la LAN podría leer los ficheros del repositorio. Está en `127.0.0.1`
y por eso se fija explícitamente en los ajustes (`## 6`).

## 6. Lo aplicado

`.vscode/settings.json`, nuevo:

```jsonc
{
  "livePreview.openPreviewTarget": "Embedded Preview",
  "livePreview.useIntegratedBrowser": true,
  "livePreview.hostIP": "127.0.0.1"
}
```

Qué compra cada ajuste:

- **`openPreviewTarget` + `useIntegratedBrowser`** — el preview embebido vive en
  el navegador simple de VS Code, y su `Origin` es `vscode-webview://…`, que el
  servidor acepta siempre. Es la **única** combinación que no depende de cómo se
  escriba la URL, así que es la que elimina el error en lugar de trasladarlo.
- **`hostIP: "127.0.0.1"`** — fija el bucle local y deja escrito el porqué, para
  que nadie lo cambie por `0.0.0.0` sin enterarse.

Con esto el auto-refresh vuelve a funcionar y la consola queda limpia.

**Honestidad sobre el alcance del arreglo:** `openPreviewTarget` ya valía
`"Embedded Preview"` por defecto, así que ese ajuste no cambia el
comportamiento de quien ya usaba el preview embebido; lo que hace es **fijarlo y
documentarlo**. El ajuste que resuelve el caso de quien abre en un navegador
externo no existe: con navegador externo hay que escribir la URL con `127.0.0.1`
exactamente, nunca con `localhost`, porque el servidor solo acepta una de las dos
formas. No hay ningún valor de `hostIP` que acepte las dos.

## 7. Por qué no se parchea la extensión

Podríaarse "arreglar" una línea de `out/extension.js`, y sería la decisión
equivocada:

- Es un **bundle minificado** de Microsoft: cualquier edición se pierde al
  actualizar la extensión.
- **Debilita el control.** La comparación de `Origin` es la única defensa real
  (`## 4.1`); relajar el `===` es justo el agujero que el código previene.
- Es software de terceros **sin soporte**. El repositorio tiene
  [`THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md) y una
  [`LICENSE`](../../LICENSE) propia; meter mano en un bundle ajeno ensucia
  provenance.

La regla que se aplicó es la de CORS: **no se desactiva el filtro, se configura
el origen**.

## 9. La alternativa que ya tiene el proyecto

Para lo que sea de producción, Live Server no es la herramienta: el repositorio
trae servidor propio, y es más fiel a lo desplegado.

```bash
npm run servidor   # http://localhost:8000
```

| | Live Server | `npm run servidor` |
|---|---|---|
| Puerto | `3000` | `8000` (`PORT` lo cambia) |
| Escucha | `127.0.0.1` | `127.0.0.1` **y** `::1`, a propósito |
| Cabecera CSP | **No** | **Sí**, la misma de `vercel.json` |
| Auto-refresh | Sí | No |
| Conflicto de puertos con Live Server | — | Ninguno, puertos distintos |

El punto que importa: **`serve.mjs` sí reparte el CSP real de producción**, y el
preview embebido de Live Server sirve sin él. Al comprobar el CSP hay que mirar
el sitio que sirve `serve.mjs`, no el que sirve la extensión.

## 10. Lo que queda pendiente

- **El bug de la extensión no está reportado.** La incoherencia del `## 3.1`
  (HTTP acepta `localhost`, WebSocket no) es de `ms-vscode.live-server` y se
  resuelve con `Ctrl+Shift+P` → *Report Issue*. Está fuera de este repositorio.
- **El token decorativo del `## 4.1`** no tiene arreglo local: depende de
  Microsoft.
- **No verificado**: que el auto-refresh funcione tras el cambio. El arranque de
  Live Server ocurre dentro de VS Code y no se puede comprobar desde aquí
  (`## 6`); lo verificado es el `101` del handshake con `Origin` de preview
  embebido (`## 4`), que es la condición que fallaba.
