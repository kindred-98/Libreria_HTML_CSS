(PR #21 mergeada, `v1.1.0` publicada, 1.018 demos en catálogo, 0 issues

## 6. CI nuevo: control de no regresión en el catálogo

Para que un PR no baje el número de demos por error, se añade un job
ligero en `.github/workflows/validate.yml`. Diseño:

```yaml
- name: Recuento de demos
  run: |
    prev=$(curl -s "${{ github.event.pull_request.base.repo.owner.login }}:${{ github.event.pull_request.base.ref }}:Web/data/catalog.json" || true)
    prev_n=$(printf "%s" "$prev" | node -e 'let s="";process.stdin.on("data",c=>s+=c).on("end",()=>{try{console.log(JSON.parse(s).length||0)}catch{console.log(0)}})')
    npm run catalogo
    new_n=$(node -e 'console.log(JSON.parse(require("fs").readFileSync("Web/data/catalog.json","utf8")).length)')
    if [ "$new_n" -lt "$prev_n" ]; then
      echo "::error::El catálogo pasó de $prev_n a $new_n demos; ningún PR puede reducir el total."
      exit 1
    fi
    echo "Demos: $new_n (anterior: $prev_n)"
```

Queda en `TBD` hasta que se implemente en CI. Mientras tanto, la revisión
humana en cada PR de demo verificará que `npm run catalogo` añade al menos
un `id` por encima del catálogo base.

## 7. Monitorización tras release

Durante las dos semanas posteriores a la `v1.2.0` se vigila:

- **Tráfico y uso de demos en producción** (Vercel Analytics o similar):
  ver qué demos se sirven en el preview, qué autores importan.
- **Rastreo de Google Search Console** para confirmar que la indexación
  recoge los nuevos `index.html` después de un sitemap fresco.
- **Errores de consola** en el smoke test (`validar:demos`): si alguno se
  rompe por la nueva versión de Chromium, hay que parchear antes de la
  v1.2.1.
- **Tasa de Lighthouse**: si una demo nueva degrada el LCP de portada, se
  retrasa su merge hasta optimizarla.

## 8. Riesgos y mitigación

- **Riesgo**: demos que rompen el smoke test por su propio JS.
  **Mitigación**: validación en CI por demo (e2e individual), opcional, con
  `validar:demos` reducido a ese id.
- **Riesgo**: SonarCloud abre falsos positivos en el código nuevo.
  **Mitigación**: revisar la `Docs/Sonar_decisiones.md` antes de cerrar
  issues como "intentional" en la UI.
- **Riesgo**: Vercel no aprueba por uso de la API deprecada de Chromium.
  **Mitigación**: monitorizar el log del job `Analizar (javascript-typescript)`
  y las releases de `playwright` y `chrome-launcher`.
- **Riesgo**: un ZIP queda sin `LICENSE` y desactiva la descarga.
  **Mitigación**: `npm run zips` falla si falta; se documenta en
  `CONTRIBUTING.md` §1.

## 9. Cómo abrir issues/PRs

- Cada demo nuevo va en un issue del tipo
  `[Demo] <nombre> (<categoría>)` con checklist:
  1. Carpeta creada.
  2. `index.html` con `<title>` único.
  3. `styles.css` y/o `script.js` con estilos sin errores de `prettier`.
  4. `LICENSE` MIT o COPY de la de la raíz.
  5. PR abierto con la URL del preview de Vercel.
- Plantilla de PR (`Docs/PULL_REQUEST_TEMPLATE/demo.md` cuando se cree) con
  capturas, métricas Lighthouse del preview y enlaces a las páginas que
  enlaza dentro del demo (si las hay).
